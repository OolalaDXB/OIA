Tables : `vis.client`, `vis.site`, `vis.subject`, `vis.subject_site`, `vis.window`, `vis.window_missing_day`, `vis.evidence`. Trigger `evidence_set_hash` (SHA-256 bytea calculé côté serveur sur `raw_text`). Triggers `evidence_block_update` et `evidence_block_delete` (toute mutation est refusée avec code SQLSTATE `25006 read_only_sql_transaction`). RLS sur toutes les tables du schéma (hors `vis.client`, lecture admin seulement), policy fondée sur `current_setting('vis.client_id', true)` — le contrat `Tenanted` de `src/tenancy.ts` est la source TS, le GUC `vis.client_id` est la source SQL. FK composite `evidence(subject_id, client_id) → subject(id, client_id)` : un sujet ne peut pas changer de client sous ses preuves.
- Tests : `scripts/test-evidence-migration.sh` démarre un conteneur `oia-vis-test-pg` (Postgres 16-alpine, port 127.0.0.1:55432, mot de passe aléatoire, pas de volume), applique la migration, crée un rôle `oia_vis_app` (NOBYPASSRLS), insère pour deux clients fictifs puis vérifie :
  1. INSERT valide + raw_sha256 calculé par le serveur (b2394f8…).
  2. Un raw_sha256 fourni côté client est **écrasé** par le trigger.
  3. UPDATE refusée.
  4. DELETE refusée.
  5. Le client B voit 1 seule ligne (la sienne) et ne peut pas insérer une ligne « pour A ».
  Résultat : **5/5 PASS**. Le conteneur est supprimé en fin de test (trap EXIT).
